# v3.0 实时告警设计（Alerting Design）

> 版本：v1（2026-10-17）｜状态：设计定稿，MVP 已实现；**Feishu 通道 2026-10-17 14:00 UTC 实测成功**，进入影子模式
> 定位：**交付层升级，不是新信号**。告警永不改变卡片、仓位与 `gor_latest.json`。
> 一句话：**盘中拉报价 → 用同一套纯函数算临时卡片 → 与上次状态比较 → 只在状态跃迁时通知 → 全程留痕。**

---

## 1. 目标与非目标

### 成功标准
| 维度 | 目标 |
|---|---|
| 延迟 | P0：典型 5–20 分钟（GitHub Actions 尽力而为）；P1：收盘确认后 |
| 覆盖 | 硬止损、投降签名、区间/仓位/裁决变化、合同里程碑、数据故障 |
| 噪音 | ≤ 5 条/周；每条都能对应到一条规则 |
| 可靠性 | 双通道、重试 3 次、失败开 Issue、外部心跳兜底 |
| 可审计 | `alerts/log.jsonl`：规则、数值、阈值、报价时间、来源、投递结果 |
| 纪律 | 告警不改变仓位；卡片是唯一事实源 |

### 非目标
- 不做 tick 级 / 秒级告警（框架是日频的）。
- 不做主观“提醒”“感觉要崩”的消息。
- 不把告警接入交易执行。
- 不用 Buttondown 发实时告警（它是订阅信工具）。

## 2. 架构：状态差分，而不是平行规则引擎

```
每 15 分钟：
  拉报价（WTI / Gold / VIX / DXY / 10Y）
    → 调用与每日管道相同的纯函数（compute_gor / screener.evaluate）
    → 得到状态向量 state
    → 与 alerts/state.json 比较
    → 跃迁则生成 alert（P0/P1/P2/P3）
    → 追加 alerts/log.jsonl；更新 state.json
```

**为什么不能另外写一套阈值**：机器的硬止损是 `60 日均线 × 0.85 或绝对底 60`，不是固定 75；恐慌门槛是 VIX 滚动十年 P80（当前约 22.46），不是固定 22.5。平行规则迟早漂移。

### 状态向量（state）
```json
{
  "updated": "2026-10-17 12:00",
  "regime": "修复周期",
  "position": 30,
  "verdict": "红",
  "npass": 1,
  "vix": 16.46,
  "vix_thr": 22.46,
  "oil_pctl": 0.967,
  "s2": false,
  "s3": false,
  "gor_wti": 41.11,
  "gor_brent": 38.78,
  "wti": 101.84,
  "gold": 4186.5,
  "hard_stop": false,
  "hard_stop_thr": 62.5,
  "contract_completion": 0.847,
  "contract_target_hit": false
}
```

## 3. 规则表

### P0 · 立即（双通道）
| rule | 条件 | 说明 |
|---|---|---|
| `hard_stop` | `WTI < 60日均线 × 0.85` **或** `WTI < 60` | 用机器动态规则；盘中允许 2 次连续确认 |
| `capitulation` | `s2=true`（VIX≥P80）**且** `s3=true`（油≤P25） | 机器真正的扳机；只在首次由 false→true 时发 |
| `data_failure` | 报价 >30 分钟未更新 / 双源偏差 >1% / JSON 契约失败 | 不发价格告警，只发运维告警 |

### P1 · 状态变化（单通道 + 日志）
| rule | 条件 | 确认方式 |
|---|---|---|
| `regime_change` | GOR 跨越 45 / 30 / 20 | 收盘确认，避免盘中假突破 |
| `position_change` | `final_position` 变化 ≥ 10pt | 当日卡片 |
| `verdict_change` | 红→黄→绿（或反向） | 当日卡片 |
| `contract_target` | WTI ≥ $107.60 | 盘中触及即可 |
| `contract_90` | 合同完成度 ≥ 90% / 100% | 盘中触及即可 |

### P2 · 观察（**08:30 BJT 摘要推送**，不即时）
- GOR 跨越 42 / 40 / 38（非区间切换）
- VIX 跨越 P80 但油未到底部四分位
- DXY > 101 / < 98；10Y > 4.5
- 油分位进入 ≤ 25%

### P3 · 运维
- 数据陈旧、源偏差、JSON 契约失败、投递失败、心跳缺失。

## 4. 状态机、迟滞与去重

- 每个规则保存 `{state, last_value, last_sent, last_id}`。
- **只发跃迁**（normal→triggered 或 triggered→normal 的恢复通知可选）。
- **迟滞**：
  - 硬止损：`WTI > 60日均线 × 0.90` 才重新武装。
  - 区间：反向跨越需连续 2 个收盘确认。
  - 合同：达到后不重复；只在首次触发时发。
- **冷却**：同一 P1 规则 24 小时最多 1 条；P0 不重复轰炸，但每日摘要保留“未解除”状态。
- **幂等**：`alert_id = {UTC时间桶}-{rule}`；重试不重复发送。

## 5. 数据质量

| 检查 | 处理 |
|---|---|
| 报价时间戳 > 30 分钟（盘中） | 抑制价格告警，发 P3 |
| 双源偏差 > 1% | 抑制，发 P3 |
| WTI ≤ 0（2020 负油价） | 视为异常，禁止触发“便宜”规则 |
| 合约换月（CL=F 每月 20 日前后） | 用连续合约或换月日抑制 |
| Brent 口径 | Yahoo BZ=F 主 → 腾讯 BZ → FRED/EIA 现货（滞后）→ akshare；仅全部失败时用 WTI×1.06，并在卡片 `brent_source` 标注“合成” |
| FX 数据滞后 ~1 周 | 仅用于每日前哨，不用于盘中 P0 |

## 6. 调度

- **GitHub Actions**：`intraday.yml`，cron `*/15 12-21 * * 1-5`（UTC），其余时段每小时；`workflow_dispatch` 手测。
- **每日收盘**：`daily.yml` 末尾追加 `alert_check --send --write`，负责区间/仓位/裁决等 P1（盘中路径只发 P0/合同）。
- **每日 08:30（00:30 UTC）**：`digest.yml` 发送 P1+P2 摘要（过去 24h 变化 + 当前卡片）；P0 不重复。
- **并发**：`concurrency: alert-check`，`cancel-in-progress: false`；push 前 `git pull --rebase`。
- **延迟诚实**：GitHub schedule 是 best-effort；对外写“near-real-time（典型 5–20 分钟）”，不写“实时”。
- **窗口**：原油近 24h；VIX/DXY/10Y 美盘时段；周末/节假日不轮询。
- **外部 runner**：若未来需要 <5 分钟，把 `alert_check.py` 原样搬到 VPS/Cloudflare Cron；接口不变。

## 7. 通道与消息模板

优先级：飞书群机器人 → Telegram Bot → 钉钉/ServerChan → **GitHub Issue（仅在主通道全部失败时兜底，避免每条告警都开 Issue）**。Buttondown 只做每周摘要。
接入向导：[docs/feishu-setup.html](feishu-setup.html)（扫码/3 步）或 `python scripts/feishu_setup.py`（测试 + 自动写 Secret）。

```
🔴 P0 · 硬止损触发
规则：WTI < 60日均线 × 0.85
现值：$58.20（阈值 $63.80）
报价时间：2026-10-17 15:10 BJT · 来源 Yahoo
状态：仓位建议 30% → 5%（下一交易日生效）
卡片：justinjchen-cornell.github.io/Deep-Risk-OPP
什么会让我改口：WTI 收复 $63.80 并站稳 2 个收盘
ID：2026-10-17T07:12Z-hard_stop
```

消息必须包含：级别、规则、现值 vs 阈值、报价时间/来源、卡片链接、可证伪条件、ID。

## 8. 可靠性

- **心跳**：每次检查写 `alerts/heartbeat.json`；watchdog 盘中 2 小时未更新 → 开 Issue。
- **死手开关**：healthchecks.io 每 15 分钟 ping；漏 30 分钟 → 邮件/Telegram。
- **重试**：投递失败指数退避 3 次；全失败 → GitHub Issue + 次日摘要。
- **密钥**：GitHub Actions Secrets；`::add-mask::`；绝不入库。

## 9. 文件与职责

| 文件 | 职责 |
|---|---|
| `data_pipeline/alerts.py` | 状态向量、规则评估、状态/日志读写（纯函数，可测） |
| `scripts/alert_check.py` | CLI：读卡片/报价 → 评估 → dry-run 输出 / `--write` 持久化 |
| `scripts/precrisis_watch.py` | B/C 类前哨：7 项每日打分，输出 md/json（不接通道） |
| `alerts/state_daily.json` / `state_intraday.json` | 上次状态（按模式分开；只在基线/跃迁时更新） |
| `alerts/digest_state.json` | 上次摘要时间（避免重复） |
| `alerts/log.jsonl` | append-only 告警日志 |
| `.github/workflows/intraday.yml` | 15 分钟调度 |
| `tests/test_alert_check.py` | 规则与状态机单测 |

## 10. 分阶段上线

| 阶段 | 内容 | 工期 |
|---|---|---|
| P0 | 设计 + 规则表（本文） | 0.5 天 |
| P1 | `alerts.py` + `alert_check.py` + 单测（dry-run） | 2 天 |
| P2 | `intraday.yml` + secrets，影子模式 | 0.5 天 |
| P3 | 影子 2 周：只日志、不发送；统计误报/延迟/噪音 | 2 周 |
| P4 | 启用 P0/P1 + 08:30 P2 摘要；心跳；runbook | 0.5 天 |
| P5 | 外部死手、月度告警审计 | 1 天 |

**MVP 分两层**：评估层已包含核心 4 条（硬止损、投降签名、合同目标、数据故障）+ 区间/仓位/裁决的 P1/P2 骨架；**发送层在影子期只启用核心 4 条**，其余先记日志不推送。

## 11. 告警审计指标

- 触发→送达延迟（中位数/P95）
- 误报率（按规则定义）
- 漏报（与每日卡片对照）
- 每周告警条数（目标 ≤5）
- 投递成功率（目标 ≥99%）

每月公开一次；连续两月误报超标的规则，必须改阈值或降级。

## 12. 与“危机前哨”的关系

机器扳机只覆盖 A 类（增长/商品型）危机。B 类（货币/财政/期限溢价）与 C 类（通胀/供给）由 `scripts/precrisis_watch.py` 每日打分，作为 P2 摘要，不改变仓位。两者关系：

```
A 类：VIX≥P80 + 油≤P25 → 扳机 → 告警 → 机器行动
B/C 类：实际利率/信用利差/期限结构/FX/避险失效/实物压力 → 前哨 → 摘要 → 人工判断
```

前哨转红不是加仓理由；它是“把安全带系好”的提醒。

**评分口径**：每项 🟢=0 / 🟠=1 / 🔴=2；总分 0–14。**0–3 绿、4–6 琥珀、7+ 红**。只用于每日摘要，不触发仓位。
